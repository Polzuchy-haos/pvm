# Высокоуровневый язык PVM (`.hlc`)

Маленький C-подобный язык, который компилятор `pvmcc` переводит в текст
ассемблера `.pvms` (см. `docs/pvms-language.md`) — дальше он идёт через
`pvmc` без единой правки. Компилятор сам считает раскладку кадра
(`ENTER`/`LEAVE`/`LOADFP`/`STOREFP`), расставляет метки для `if`/`while`/`for`
и подставляет адреса глобальных переменных — вручную это делать не нужно.

**Устранение мёртвого кода.** В итоговый `.pvms` попадают только `main` и всё,
что из неё достижимо по графу вызовов (он полностью статический — указателей
на функции в языке нет), и только те глобальные/массивы, на которые реально
где-то есть ссылка. Неиспользуемые функции не занимают место в байткоде,
неиспользуемые глобальные не занимают ячейку RAM (важно — она всего 32 слова).
При этом **компилируются и проверяются на ошибки все функции без исключения**,
включая недостижимые — устранение мёртвого кода происходит уже после проверки,
как отбрасывание неиспользуемых секций линковщиком, а не как пропуск
компиляции. Это особенно чувствительно при `import`: можно подключить целый
файл-библиотеку (`import mathlib;`) и использовать только часть его функций —
остальное не попадёт в прошивку.

## import

```c
import mathlib;   // найдётся в lib/ рядом с pvmcc (см. поиск ниже)
```

По аналогии с `.import` в `.pvms`: имя без кавычек и без расширения.
Подстановка происходит рекурсивно и на уровне токенов — ещё до разбора, так
что объявления подключённого файла становятся видны как обычные объявления
этого же файла (и попадают под те же правила — повторное имя функции/
переменной между файлами это тоже ошибка "redefined"). Циклические импорты
обнаруживаются и являются ошибкой компиляции. `import` может стоять в любом
месте файла, но по смыслу — директива верхнего уровня, как и `.const`/
`.import` в `.pvms`.

Файл, который только подключается (как `lib/mathlib.hlc`), не обязан
содержать `main()` — требование `void main()` проверяется один раз, для
итоговой подключённой программы целиком.

### Поиск файла

Как у `#include` в C — по каждой директории ищется сначала точное имя, потом
`имя + ".hlc"`, в таком порядке:

1. **рядом с компилируемым файлом** (директория того `.hlc`, где написан
   `import`, а не рядом с "корневым" файлом, если импорт вложенный);
2. **`lib/` рядом с исполняемым файлом `pvmcc`** — путь к самому себе
   компилятор узнаёт у ОС (`GetModuleFileName` на Windows), а не через
   `argv[0]`, так что это работает даже если `pvmcc` запущен просто по имени
   через `PATH`. Сюда попадает `lib/` из корня репозитория — CMake копирует
   её рядом со собранным `pvmcc.exe` автоматически (`hlc/CMakeLists.txt`), в
   `Release/` она лежит рядом с бинарником уже готовой;
3. **пути, переданные через `-I путь`** — можно указывать флаг несколько раз,
   директории проверяются в том порядке, в котором даны в командной строке
   (`pvmcc prog.hlc -I ../common -I ../vendor`).

Если файл не нашёлся ни в одном месте — ошибка перечисляет все проверенные
директории.

## extern — вызов функции, написанной на ассемблере

```c
extern int fastmul(int a, int b) from fastmath;   // реализация — example/fastmath.pvms

void main() {
    RESULT = fastmul(6, 7);   // обычный вызов, как для любой другой функции
}
```

Объявляет сигнатуру функции без тела — компилятор трактует вызовы `fastmul(...)`
так же, как вызовы обычной `.hlc`-функции (проверяет число аргументов,
`void`/значение и т.д.), но кодогенерации тела не делает: реализация — это
метка `fastmul:` в написанном вручную `.pvms`-файле, следующая той же
конвенции вызова (`ENTER`/`LEAVE`/`LOADFP`/`STOREFP`, зарезервированный слот
результата — см. `docs/pvms-language.md`), что генерирует сам `pvmcc`.
Компилятор не может это проверить — это контракт между `.hlc`-программой и
ассемблерным файлом, как и `svc(...)`.

`from имя` резолвится **тем же поиском**, что и `import` (рядом с
компилируемым файлом → `lib/` рядом с `pvmcc` → `-I`), но с расширением
`.pvms` вместо `.hlc`, и сразу в абсолютный путь: сгенерированный `.pvms`
может оказаться в другом каталоге (например, в build-дереве), поэтому
компилятор эмиттит `.import <абсолютный путь>` — обычный `.pvms`-ассемблер
(`pvmc`) правильно подхватывает абсолютные пути в `.import`, никаких правок
в нём не понадобилось. `.import` для каждого использованного (не отброшенного
устранением мёртвого кода) `extern`-файла добавляется в вывод один раз, даже
если из него подключается несколько функций.

См. `example/extern_demo.hlc` + `example/fastmath.pvms`.

## Типы

Только один тип данных — `int` (16-битное знаковое слово, как `PVM_Word_t` в
ВМ). `void` — только как тип возврата функции, отдельного типа-переменной
`void` не существует.

Символьные литералы `'A'` — не отдельный тип, а просто ещё одна форма записи
целого числа (ASCII-код): `'A'` — то же самое, что `65`, лексер разворачивает
их в `IntLiteral` ещё до парсера. Поддержаны экранирования `'\n' '\t' '\r'
'\0' '\\' '\'' '\"'`.

## section — размеры памяти целевой ВМ

```c
section code    8192;       // байт под байткод
section ram     64;         // слов RAM: адреса 0..63
section stack   1024;       // слов стека данных
section usrsect 0x4000, 8;  // база и длина секции периферии
```

Объявляет, сколько памяти есть у **целевой** ВМ, чтобы выход за её границы был
ошибкой компиляции, а не ошибкой в рантайме на устройстве. Компилятор
использует эти размеры сам (раскладка глобальных переменных, проверка адресов
после `@`) и передаёт их ассемблеру директивами `.code`/`.ram`/`.stack`/
`.usrsect` — тот проверяет уже сгенерированный код: размер программы, цели
переходов, адреса `LOAD`/`STORE`, смещения кадра (подробности и точный список
проверок — в `docs/pvms-language.md`).

- Каждая секция объявляется не более одного раза, в любом месте файла.
- Размер — константное выражение (см. «Именованные константы»), то есть можно
  `const int PERIPH = 0x4000; section usrsect PERIPH, 8;`.
- Необъявленная секция берёт значение из `pvm/pvm.h`, поэтому файл без
  `section` компилируется как раньше. Длина `usrsect` — исключение: константы
  для неё в `pvm.h` нет, и пока она не объявлена, адрес от базы и выше
  считается допустимым.
- Объявлять можно **меньше**, чем есть у ВМ на самом деле — тогда проверки
  просто строже. Объявление большего размера, чем у реального устройства, ВМ
  не заметит: `section` — это обещание компилятору, а не настройка ВМ.

Пример целиком — `example/sections_demo.hlc`; примеры того, что теперь не
компилируется, — в `example/bounds/`.

### Анализ глубины стека

`pvmcc` считает, сколько слов стека программа займёт в худшем случае, и
сообщает результат:

```
pvmcc: stack: worst case 12 of 1024 words
```

Та же строка попадает комментарием в начало сгенерированного `.pvms`. Если
худший случай не помещается в `section stack` — это ошибка компиляции.

Как считается: при генерации кода компилятор отслеживает глубину стека внутри
каждой функции (включая промежуточные значения выражений и ветвления — на
метке берётся глубина, с которой на неё прыгают, поэтому две ветки тернарного
оператора не складываются), а затем идёт по графу вызовов и берёт максимум по
всем цепочкам: глубина в точке вызова + одно слово на адрес возврата + то, что
нужно самой вызываемой функции.

Ограничения — честные, их стоит знать:

- **Рекурсия** делает глубину функцией входных данных, а не свойством кода.
  Цикл в графе вызовов не разворачивается: компилятор сообщает
  `recursion found -- worst-case depth cannot be bounded` и не выдаёт числа
  (ошибкой это не считается).
- **Функции на ассемблере** (`extern ... from ...;`) компилятору не видны, их
  собственный расход стека в сумму не входит. В этом случае к строке
  добавляется `not counting hand-written asm functions`, и число нужно читать
  как нижнюю оценку.
- Оценка относится только к коду, сгенерированному из `.hlc`. Для
  вручную написанного `.pvms` анализа нет — там ассемблер проверяет лишь
  смещения `LOADFP`/`STOREFP` относительно `.stack`.

## Глобальные переменные

```c
int COUNTER;                    // обычная переменная в RAM
int COUNTER = 5;                // с начальным значением (константное выражение)
volatile int LED @ 0x4000;      // жёсткая привязка к адресу — периферия/MMIO
int table[10];                  // массив в RAM (без инициализатора)
int table2[3] = {1, 2, 3};      // массив со списком-инициализатором
int a, b = 3, c;                // несколько переменных в одном объявлении
```

`@адрес` — переменная живёт по фиксированному адресу (обычно периферия,
`>= 0x4000`), а не в авто-выделяемой ячейке RAM. Обычные (без `@`) глобальные
переменные и массивы компилятор сам раскладывает по RAM подряд, начиная с
адреса `0`, и проверяет, что они помещаются в размер RAM (см. «section»).
Адрес после `@` компилятор подвинуть не может, поэтому его он тоже проверяет —
что тот попадает либо в RAM, либо в объявленную секцию `usrsect`.

Инициализатор допускается только у не-`volatile` глобальных. И скалярный
инициализатор, и элементы `{...}`-списка для массива, и адрес после `@`, и
размер массива в `[...]` — это *константные выражения* (см. следующий
раздел): литерал, имя `const` или арифметика/побитовые операции над ними —
вычисляются компилятором целиком, в рантайм ничего не попадает.

`int arr[N] = {v0, v1, ...};` — количество значений в `{...}` обязано **точно**
совпадать с `N` (строже, чем в C, где недостающие элементы молча зануляются)
— иначе ошибка компиляции.

`int a, b = 3, c;` — одно объявление на несколько имён (тот же `int`, через
запятую); каждое имя может независимо иметь свой `@адрес`/`[размер]`/
`= инициализатор`, в том числе `volatile int X @ addr1, Y @ addr2;`.

## Именованные константы

```c
const int MAX_SPEED = 100;
const int LED_ADDR   = 0x4000;
const int LED_MASK   = 1 << 2;     // можно ссылаться на арифметику

volatile int led @ LED_ADDR;       // константа как адрес MMIO
int history[MAX_SPEED];            // константа как размер массива
int limit = MAX_SPEED / 2;         // константа в инициализаторе глобальной
```

`const int ИМЯ = <константное выражение>;` — только на верхнем уровне файла.
Ключевое отличие от обычной глобальной переменной: константа не занимает
ячейку RAM и не попадает в сгенерированный `.pvms` как отдельный символ —
каждое использование имени подставляется компилятором как `PUSH <значение>`
(либо, в адресе/размере массива, просто как число), поэтому неиспользуемая
константа буквально ничего не стоит.

Константное выражение может содержать: целочисленные литералы, имена ранее
объявленных `const` (объявления читаются по порядку сверху вниз — вперёд
ссылаться нельзя, как в C), унарные `- ~ !` и любые бинарные операторы
(`+ - * / & | ^ << >> == != < > <= >= && ||`) над ними. Переменные, массивы,
вызовы функций и `svc(...)` в константном выражении недопустимы — ошибка
компиляции. Присвоение константе (`ИМЯ = ...;`) — тоже ошибка компиляции.

Имя константы не может совпадать с именем функции, глобальной переменной
или другой константы.

## Функции

```c
int square(int x) {
    return x * x;
}

void increment() {
    LED = LED + 1;
}

void main() {
    ...
}
```

- `main` обязателен и должен быть объявлен ровно как `void main()` — без
  параметров и без возвращаемого значения. Причина: `main` — точка входа
  (`.entry main`), у неё нет вызывающего и, соответственно, некуда возвращать
  результат обычным `RET`; выход из `main` (явный `return;` или просто конец
  функции) компилируется в `HALT`, а не в `RET`.
- Любая другая функция с `return expr;` на всех путях выполнения, если она не
  `void`; `void`-функция не может возвращать значение (`return;` — можно).
- Аргументы передаются по значению, только `int`. Количество аргументов в
  вызове обязано совпадать с объявлением — иначе ошибка компиляции.
- Рекурсия поддерживается — каждый вызов получает свой кадр (`ENTER`/`LEAVE`).

## svc — вызов в Си-код

```c
svc(1, 42);              // как оператор — результат отбрасывается
RESULT = svc(2, 3, 4);   // как выражение — используем возвращённое значение
```

`svc(номер, аргументы...)` компилируется в низкоуровневую инструкцию `SVC`
(см. `docs/pvms-language.md`): аргументы пушатся слева направо, следом номер
вызова, затем `SVC`. Это встроенная языковая конструкция, а не обычный вызов
функции — компилятор не проверяет и не знает ни число аргументов, ни то,
возвращает ли конкретный номер значение: это контракт между `.hlc`-программой
и Си-обработчиком, зарегистрированным через `PVM_RegisterSvc` (как и в
`.pvms`, компилятор просто доверяет, что они согласованы). По конвенции
каждый обработчик кладёт на стек ровно один результат — `svc(...)` всегда
ведёт себя как обычное выражение с одним значением, годится и как оператор
(`svc(1, 42);`), и как часть выражения (`x = svc(2, 3, 4);`).

В `simulator/pvmsim.c` сейчас зарегистрированы `SVC #0` (`Svc_Tick`), `#1`
(`Svc_Print`), `#2` (`Svc_Add`) — это конкретная таблица симулятора, не часть
языка. Пример посложнее, показывающий, зачем вообще может понадобиться `svc`
— библиотека `lib/time.hlc`:

- `int Time_GetTick()` — текущий тик (обёртка над `svc(0)`);
- `int Time_Elapsed(int old)` — разница с учётом переполнения 16-битного
  счётчика, реализовано целиком на `.hlc`, без единой правки в ВМ (обычное
  `-` и так работает по модулю 2¹⁶);
- `void Time_Delay(int ticks)` — busy-wait на `ticks` отсчётов поверх двух
  предыдущих; на МК с настоящим таймером за `SVC #0` — реальная задержка, без
  единой правки в этом коде (см. `example/blink.hlc`).

См. также `example/time_demo.hlc` (проверка `Time_Elapsed` на переполнении).

См. `example/svc_demo.hlc` и обработчики `Svc_Print`/`Svc_Add` в
`simulator/pvmsim.c`.

## Локальные переменные — важное ограничение

```c
void f() {
    int a;        // OK — самое начало функции
    int b = 1;    // OK
    int c, d = 2; // OK — несколько имён в одном "int", как и у глобальных
    a = 2;        // дальше — обычные операторы, ещё один "int" здесь уже нельзя
}
```

**Все локальные объявления обязаны идти единым блоком в самом начале тела
функции**, до любого другого оператора (правило в духе C89) — включая тело
`if`/`while`/`for` и `for`-инициализатор: там объявлять локальные нельзя,
только использовать уже объявленные вверху. Это не забытая фича, а осознанное
ограничение: раскладка локальных на `FP` — статическая (компилятор один раз
на этапе компиляции решает, какой переменной какое смещение соответствует), и
это верно только если каждое объявление гарантированно выполняется ровно один
раз за вызов функции. Объявление внутри цикла или условия исполнялось бы
переменное число раз и рассинхронизировало бы адресацию остального кадра.

**Локальных массивов не бывает** — только глобальные. `LOADFP`/`STOREFP`
берут константное смещение, а не индекс со стека, поэтому массив на стеке
кадра адресовать нечем; массив в RAM адресуется как `база + индекс` через
`LOADI`/`STOREI`, что и делает компилятор для глобальных массивов.

Блочной вложенности/тени переменных нет: имена локальных и параметров функции
— в одном плоском пространстве имён на всю функцию.

## Операторы

```c
{ ... }                              // блок
if (cond) stmt [else stmt]
while (cond) stmt
do stmt while (cond);                // тело выполняется минимум один раз
for (простой_оператор?; cond?; простой_оператор?) stmt
return [expr];
halt;
имя = expr;
имя += expr;                         // и -= *= /= &= |= ^= <<= >>=
имя++;  имя--;
имя[индекс] = expr;
имя(аргументы);                      // вызов как оператор
```

`do ... while (cond);` — условие проверяется **после** тела, поэтому оно
всегда выполняется хотя бы раз (в отличие от `while`).

Составные присваивания и `++`/`--` — чистый сахар: парсер разворачивает
`x += e` в `x = x + e`, а `x++`/`x--` в `x = x + 1`/`x = x - 1` ещё до
кодогенерации, так что для компилятора это буквально то же самое обычное
присваивание (см. `hlc/parser.cpp`, `MakeCompoundAssign`). Работают только
для простого имени (локальной/глобальной переменной, параметра) — **не для
элемента массива** (`arr[i] += 1;` не поддерживается): такое же
разворачивание для массива вычислило бы индекс `i` дважды, что незаметно
ломается, если у индекса есть побочный эффект (вызов функции, `svc`).

## Выражения и операторы (по убыванию приоритета)

| Приоритет | Операторы | Ассоциативность |
|---|---|---|
| низший | `?:` (тернарный) | справа налево |
| | `\|\|` | слева направо |
| | `&&` | слева направо |
| | `==` `!=` | слева направо |
| | `<` `>` `<=` `>=` | слева направо |
| | `\|` | слева направо |
| | `^` | слева направо |
| | `&` | слева направо |
| | `<<` `>>` | слева направо |
| | `+` `-` | слева направо |
| | `*` `/` | слева направо |
| высший | унарные `-` `!` `~` | справа налево |

Плюс индексация `arr[i]` (только для глобальных массивов), вызов функции
`f(...)`, скобки `(expr)`, целочисленные и символьные литералы (`123`, `0x7B`,
`'A'`), `sizeof(имя)`.

`cond ? a : b` — как в C: вычисляется ровно одна из веток (`a`, если `cond`
не ноль, иначе `b`), обе оставляют по одному значению на стеке — компилятор
это не отличает от `if`/`else` с точки зрения кодогенерации (`JZ`/`JMP`).
Правоассоциативен, поэтому `a ? b : c ? d : e` — это `a ? b : (c ? d : e)`.
Также работает как константное выражение (`const`, `@адрес`, `[размер]`) —
вычисляется только выбранная ветка, поэтому `cond ? x : 1 / 0` не упадёт на
делении на ноль, если `cond` истинно.

`sizeof(имя)` — количество элементов глобального массива `имя` (для не-массива
— ошибка компиляции), известное уже на этапе компиляции: сворачивается прямо
в `PUSH <размер>`, как литерал. Именно поэтому, в отличие от обычного чтения
элемента массива, `sizeof` **не** отмечает массив как использованный — если
во всей программе массив нигде, кроме `sizeof(...)`, не встречается, он не
получит ячейку RAM вообще (устранение мёртвого кода отбросит его целиком, а
число уже подставлено). Доступен только внутри тела функций — не в `const`
и не в `@адрес`/`[размер]`, потому что на момент их вычисления список
глобальных ещё не готов (см. `hlc/codegen.cpp`, `Codegen::Run`).

`&&`/`||` — **с коротким замыканием**, как в C (правая часть не вычисляется,
если результат уже известен по левой), результат всегда нормализован к `0`
или `1`. Присваивание — только как оператор верхнего уровня внутри
`простой_оператор` (`a = b = 5` и `if ((a = f()) != 0)` не поддерживаются),
но как выражение оно **возвращает присвоенное значение** (поэтому его можно
использовать, например, в `for`-шаге).

## Комментарии

`// до конца строки` и `/* блок */` — как в C (независимо от `#`-комментариев
`.pvms`, у языка свой лексер).

## Чего сознательно нет в этой версии

- Типов кроме `int`/`void` (нет `char`, `bool`, `float`, указателей, `struct`).
- Локальных массивов (см. выше) и многомерных массивов.
- Блочной области видимости/тени переменных.
- Присваивания как части произвольного выражения.
- Анализа "все ли пути функции возвращают значение" — компилятор просто
  всегда добавляет `LEAVE`/`RET` (или `LEAVE`/`HALT` для `main`) в конец тела
  функции, даже если до этого уже был явный `return` на всех путях
  (недостижимый код на пару байт, не баг).

## Пример целиком

```c
int arr[5];
int SUM;

void fill() {
    int i;
    for (i = 0; i < 5; i = i + 1) {
        arr[i] = i * 2;
    }
}

int total() {
    int i;
    int sum;
    sum = 0;
    for (i = 0; i < 5; i = i + 1) {
        sum = sum + arr[i];
    }
    return sum;
}

void main() {
    fill();
    SUM = total();   // 0+2+4+6+8 = 20
}
```

Больше примеров: `example/square.hlc` (аргумент + возврат), `example/counter.hlc`
(MMIO + `while`), `example/blink.hlc` (бесконечный цикл + программная задержка),
`example/arrays_and_logic.hlc` (массивы, `for`, все сравнения, `&&`/`||`),
`example/import_demo.hlc` + `lib/mathlib.hlc` (`import`),
`example/svc_demo.hlc` (`svc(...)`), `example/extern_demo.hlc` +
`example/fastmath.pvms` (`extern ... from ...;`), `lib/time.hlc` +
`example/time_demo.hlc` (учёт времени поверх `svc`).

## Диагностика ошибок

Компилятор останавливается на первой ошибке и печатает `файл:строка: error:
сообщение` в stderr, код возврата `1`. Проверяются: неизвестные
идентификаторы/функции, несовпадение числа аргументов, использование `void`-
функции как значения, локальные объявления не в начале функции, локальные
массивы, переполнение RAM глобальными, `main` с параметрами или не `void`, и
т.д.
