# `pvminit` — генератор сборочных и отладочных скриптов

Своя программа на `.hlc` — это всегда одни и те же несколько файлов вокруг
неё: чем собрать, чем запустить, чем отладить и как объяснить всё это VS Code.
Файлы небольшие, но написать их с нуля значит помнить порядок вызова `pvmcc` и
`pvmc`, все нужные флаги (`-l`, `-g`) и полный путь до каждой утилиты. `pvminit`
пишет их за вас:

```
pvminit myproject --port COM6
```

```
myproject/
  main.hlc              заготовка программы (если своей ещё нет)
  Makefile              сборка, запуск, отладка, прошивочные форматы
  .gitignore            build/
  .vscode/
    launch.json         F5 — отладка .hlc в редакторе
    tasks.json          Ctrl+Shift+B — сборка, она же перед отладкой
```

Дальше всё делается обычным `make`:

```
make            собрать
make run        выполнить в симуляторе на этой машине
make debug      пошаговая отладка в ВМ
make board      то же на плате: make board PORT=COM6
```

Получаются обычные, читаемые файлы, а не скрытая система сборки — их можно и
нужно править дальше руками. Поэтому существующий файл `pvminit` **никогда не
перезаписывает** без `--force`.

## Зачем это программа, а не шаблон в документации

Единственное, чего такие файлы не могут узнать сами — где лежат утилиты.
`pvminit` этот путь находит и подставляет в то, что создаёт; скопированный из
README шаблон пришлось бы править по месту, а это ровно то, что раздражает.

Ищет он так:

1. `--tools`, если он задан явно;
2. **каталог, из которого запустили сам `pvminit`** — если в нём лежат `pvmc` и
   `pvmcc`. Благодаря этому `cd <тулчейн> && pvminit <проект>` значит именно то,
   на что похоже, и одной копией `pvminit` можно настраивать проекты на разные
   сборки тулчейна;
3. иначе — каталог, где лежит сам `pvminit.exe`. Это обычный случай: генератор
   вызывают откуда угодно, и путь в каталог без `pvmc` дал бы только проект,
   который не собирается.

Какой из вариантов сработал, `pvminit` печатает:

```
tools:  F:/Project/pvm/Release  (beside pvminit: no tools in the current directory)
```

## Ключи

```
pvminit [каталог] [ключи]
```

| Ключ | Что делает |
|---|---|
| `-m`, `--main <файл.hlc>` | главный исходник. По умолчанию: единственный `.hlc` в каталоге, а если его там нет — `main.hlc` (будет создана заготовка) |
| `-n`, `--name <имя>` | базовое имя выходных файлов (`build/имя.bin`). По умолчанию — имя главного исходника |
| `-p`, `--port <COM3>` | порт платы для отладочной конфигурации |
| `--tools <каталог>` | где лежат утилиты. По умолчанию — текущий каталог, если утилиты в нём, иначе каталог самого `pvminit` (см. выше) |
| `--make <программа>` | чем вызывать make в `tasks.json`. По умолчанию — первое из `make`, `mingw32-make`, `gmake`, что нашлось в `PATH` |
| `--no-vscode` | только `Makefile`, без `.vscode/` |
| `-f`, `--force` | перезаписывать уже существующие файлы |
| `-h`, `--help` | справка |

Каталог создаётся, если его нет. Запуск без аргументов настраивает текущий
каталог — а если в нём уже лежит ровно один `.hlc`, именно он и станет главным
исходником, без всяких ключей:

```
cd myproject
pvminit
```

## Что внутри Makefile

Все настройки — в первых строках; ниже них правится редко.

| Переменная | Зачем |
|---|---|
| `NAME` | базовое имя того, что получается в `build/` |
| `SRC` | главный `.hlc` |
| `PORT` | порт платы, можно переопределить в командной строке: `make board PORT=COM7` |
| `PVM_TOOLS` | каталог с утилитами |
| `PVMCC`, `PVMC`, `PVMSIM`, `PVMDBG`, `PVMDISASM` | каждая утилита отдельно — чтобы подменить одну, не трогая остальные |
| `INCLUDES` | дополнительные каталоги для `import ...;` (свой `lib/` рядом с `pvmcc` подхватывается и так) |

Все они объявлены через `?=`, поэтому переопределяются прямо в командной
строке, не трогая файл:

```
make PVM_TOOLS=D:/pvm/Release
```

### Цели

| Цель | Что делает |
|---|---|
| `make` / `make build` | `build/NAME.bin` + листинг `.lst` + карта отладки `.dbgmap` |
| `make run` | собрать и выполнить в `pvmsim` |
| `make debug` | собрать и открыть сессию `pvmdbg` в ВМ на этой машине |
| `make board` | то же, но на плате через последовательный порт |
| `make hex` | Intel HEX — для прошивальщика |
| `make carray` | байткод массивом C — чтобы вшить в прошивку |
| `make disasm` | дизассемблировать собранный `.bin` |
| `make clean` | удалить каталог сборки |

### Три неочевидные вещи в нём

**Исходник компилируется по абсолютному пути** (`$(CURDIR)/$(SRC)`). Ровно тот
путь, с которым был вызван `pvmcc`, попадает в карту отладки, а VS Code
открывает по нему файл, когда отладчик встаёт на строку. С относительным путём
подсветка строки молча не работала бы: каталог, относительно которого редактор
его раскроет, ничем не задан.

**`.bin`, `.lst` и `.dbgmap` рождаются одной командой,** и правило в Makefile
одно — на `.bin`. Три отдельных правила заставили бы make вызвать ассемблер
трижды.

**Пересборка завязана на все `.hlc` рядом сразу** (`$(wildcard *.hlc)`), а не
только на главный: какие файлы подключены через `import`, знает лишь
компилятор, и наружу он этого пока не сообщает. Лишний вызов `pvmcc` дешевле
правки, которую сборка не заметила.

## Отладка в VS Code

Нужно установленное расширение PVM — см. `vscode-extension/README.md` рядом с
утилитами. Дальше **F5**: `tasks.json` соберёт проект (это `preLaunchTask`),
`launch.json` запустит отладчик.

Готовых конфигураций две:

- **`PVM: <имя> в ВМ на этой машине`** — программа выполняется виртуальной
  машиной внутри `pvmdbg`, никакого железа не нужно;
- **`PVM: плата на <порт>`** — тот же интерфейс, но шаги делает настоящая
  плата. У платы программа своя, уже залитая в прошивку, поэтому `.bin` ей не
  передаётся — а карта отладки указывается обязательно и должна быть от **той
  же** сборки, что и прошивка.

`Ctrl+Shift+B` собирает проект без запуска отладчика. Ошибки `pvmcc` и `pvmc`
разбираются `problemMatcher`-ом и попадают в панель Problems кликабельным
списком.

## Несколько программ в одном каталоге

`pvminit` настраивает сборку одной главной программы — этого хватает
подавляющему большинству прошивок. Если программ действительно несколько,
проще всего сгенерировать по каталогу на каждую:

```
pvminit blink  --main blink.hlc
pvminit sensor --main sensor.hlc
```

Общий код кладётся рядом и подключается через `import`, а каталог с ним
указывается в `INCLUDES` в обоих `Makefile`.

## Что нужно, чтобы это работало

- **make** — любой GNU make. `pvminit` сам находит, как он называется на этой
  машине (`make`, `mingw32-make`, `gmake`), и пишет это в `tasks.json`.
  В сгенерированном `Makefile` явно задан `SHELL` (на Windows — `cmd.exe`):
  иначе make берёт то `cmd.exe`, то найденный в `PATH` `sh`, и одна и та же
  строка ведёт себя по-разному на двух машинах.
- **Расширение PVM для VS Code** — только для отладки по F5. `make debug`
  работает и без него, в терминале.
