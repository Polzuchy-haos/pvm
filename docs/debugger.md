# Отладчик PVM

Пошаговое выполнение программы: остановка, шаг по инструкции, точки останова,
просмотр стека. Состоит из двух частей, которые общаются кадрами по любому
байтовому потоку:

- **`pvm/pvmdbg.c`** — сторона устройства. Ничего не знает про UART: ей отдают
  буфер с принятым кадром, она кладёт в тот же буфер ответ. Компилируется в
  прошивку вместе с самой ВМ.
- **`pvmdbg`** — утилита-сессия для терминала. Умеет два транспорта: держать ВМ
  у себя в процессе (отладка на десктопе) либо говорить с платой по
  последовательному порту.
- **расширение VS Code** (`tools/vscode-pvm/`) — отладка `.hlc` прямо в
  редакторе, поверх той же `pvmdbg` (см. «В VS Code» ниже).

## Утилита

```
pvmdbg build/bytecode/square.bin   # ВМ внутри процесса утилиты
pvmdbg --port COM3                 # плата по последовательному порту, 9600 8N1
pvmdbg --port COM3 --baud 115200   # другая скорость
pvmdbg --port COM3 --map blink.dbgmap   # плюс исходник по карте отладки
pvmdbg --host square.bin --port COM3     # программа на хосте, плата только исполняет
pvmdbg --tcp 192.168.1.20:5555           # плата по TCP — через мост к её UART
```

Порт и файл вместе не имеют смысла: у платы программа уже своя, залитая в
прошивку (а чтобы исполнить на плате незалитую программу — `--host`, см. ниже).
Сессия открывается в остановленном состоянии (утилита сразу шлёт `PAUSE`) и
живёт до команды `exit` или `Ctrl+C`. Уходя, утилита шлёт `DETACH`: точки
останова снимаются, и программа продолжает работу — с того места, где стояла,
а если сессия гоняла программу с хоста (`--host`), то заново с начала, как
после `PVM_Init`. Без этого плата так и осталась бы на паузе без отладчика.

Команды, вывод и поведение у обоих транспортов одинаковые — вся сессия написана
поверх протокола и ничего не знает про то, где именно крутится ВМ. Разница
ровно одна и она в `settle`: локально утилита сама крутит цикл тиков, а плата
исполняет программу сама, и после `run` хост может лишь опрашивать `STATE`,
пока та не остановится (событий от устройства в протоколе нет).

`Ctrl+C` значит разное в зависимости от того, что происходит, — как в gdb:
во время выполнения он останавливает программу и возвращает приглашение, а в
приглашении завершает сессию. Ограничения на длительность `run` нет: прошивка
— это обычно цикл, который не заканчивается никогда, и упираться в таймаут на
каждом `run` бессмысленно. Опрос начинается частым (10 мс), чтобы близкая
точка останова сработала мгновенно, и замедляется до 250 мс — каждый вопрос
стоит плате ответа, который она обязана отправить. Молчание в ответ на
несколько запросов подряд — это уже отвалившийся провод или сброс, о чём
утилита и сообщает.

| Команда | Кратко | Что делает |
|---|---|---|
| `run` | `r` | выполнять до точки останова или конца программы |
| `step` | `s` | одна инструкция |
| `pause` | `p` | остановить |
| `reset` | | вернуть PC в начало, очистить стек, остаться остановленным |
| `state` | `i` | где PC, SP, FP и почему стоим |
| `stack [n]` | | верхние `n` слов стека (по умолчанию 8) |
| `mem` | `m` | размеры стека, RAM, usrsect и кода, как их сообщает устройство, и сколько стека занято |
| `data <адрес> [n]` | `x` | `n` слов памяти данных: RAM с `0`, usrsect с `0x4000` — адреса как в листинге переменных |
| `dis` | `d` | дизассемблировать от текущего PC |
| `break <куда>` | | точка останова: `break 0x12` или `break blink.hlc:21` |
| `clear <адрес>` | | снять |
| `breaks` | `b` | какие стоят |
| `exec <код>` | | с `--host`: выполнить несколько инструкций на устройстве (см. ниже) |
| `call <функция> [слова]` | | с `--host`: выполнить одну функцию (см. ниже) |
| `help` | `?` | список команд |
| `exit` | `quit`, `q` | закончить сессию; программа продолжает работу |

Адреса берутся из карты памяти в листинге (`pvmc … -l файл.lst`, см.
`docs/pvms-language.md`) — там указано, с какого адреса начинается каждая
функция. Но обычно адреса не нужны: см. следующий раздел.

### Исходник вместо адресов

Если есть карта отладки (`pvmc … -g файл.dbgmap`), утилита на каждой остановке
печатает строку исходника, а точки останова можно ставить по ней:

```
(pvmdbg) break blink.hlc:22
  0x000F will stop the program
(pvmdbg) run
  pc=0x000F  sp=1  fp=1  breakpoint
  -> 0x000F  0E 00 40   LOAD 0x4000
     blink.hlc:22          LED = LED ^ 1;
```

- **Локально** карта ищется сама, рядом с `.bin` (её туда кладёт `pvmc -g`).
  Нет — просто не будет строк исходника, ничего не ломается.
- **По порту** карту надо назвать явно (`--map`): программа лежит во flash
  платы, хост её никогда не видел и угадывать ему не из чего. Следить, что
  карта от той же сборки, что и прошивка, — на вас.
- Адрес между двумя записями карты относится к более ранней: одна строка
  исходника обычно превращается в несколько инструкций, помечена из них
  только первая.
- Файл исходника, которого нет на этой машине, — не ошибка: печатается
  `файл:строка` без текста. Так и будет, если прошивку собирал кто-то другой.

```
(pvmdbg) break 0x12
  0x0012 will stop the program
(pvmdbg) run
  pc=0x0012  sp=4  fp=1  breakpoint
  -> 0x0012  1A         ENTER
(pvmdbg) stack
  [0] 10      <- top
  [1] 7
(pvmdbg) dis
  -> 0x0012  1A         ENTER
     0x0013  1C FD FF   LOADFP -3
     0x0016  1C FD FF   LOADFP -3
     0x0019  07         MUL
```

Инструкция под `PC` печатается сама, после каждой остановки — иначе на каждом
шаге пришлось бы искать адрес в листинге. Байты для этого читаются **с
устройства** (команда `READ_CODE`), а не из локальной копии программы: при
работе по порту копии у хоста вообще нет, а там где есть — она может оказаться
свежее того, что реально залито в плату, и дизассемблер молча расходился бы с
машиной. Разбирает байты тот же дизассемблер, что и `pvmdisasm`, второй
таблицы мнемоник не заведено.

Периферия и SVC-обработчики те же, что у `pvmsim` (общий `simulator/pvmenv.c`),
поэтому программа под отладчиком ведёт себя так же, как при обычном прогоне.
Локально программа без точек останова и без `HALT` не подвесит утилиту: после
двух миллионов инструкций сессия сама встаёт на паузу (на плате для этого есть
`Ctrl+C`).

### По TCP (`--tcp`)

```
pvmdbg --tcp 192.168.1.20:5555 --map blink.dbgmap   # плата за мостом в сети
pvmdbg --tcp 5555                                   # только порт — эта машина
pvmdbg --host square.bin --tcp 5555                 # --host тоже работает
```

По TCP ходят ровно те же кадры, что и по последовательному порту, байт в байт.
Поэтому мосту между сетью и UART платы ничего не нужно знать о протоколе: он
просто перекладывает байты в обе стороны (одно соединение — одна плата, как и
у UART). Сборка кадров из потока, ожидание ответа и опрос работающей платы у
обоих транспортов общие (`debugger/transport_stream.c`), так что вести себя
по-разному они не могут.

- Если на том конце ещё никто не слушает, `pvmdbg` 3 секунды повторяет попытку
  соединиться — мост, запущенный одновременно с отладчиком, успеет подняться.
- `TCP_NODELAY` включён: кадры маленькие и каждый ждёт ответа, а с алгоритмом
  Нейгла запрос мог бы лишние десятки миллисекунд стоять в стеке.
- Что накопилось в мосту до подключения, выбрасывается — как `PurgeComm` у порта.

**`pvmboard`** — «плата-процесс» для работы без железа: ВМ и агент крутятся так
же, как в прошивке, только вместо UART — TCP-сокет. Периферия и SVC — как у
`pvmsim`.

```
pvmboard build/bytecode/square.bin --paused     # слушает 127.0.0.1:5555
pvmdbg --tcp 5555 --map build/bytecode/square.dbgmap
```

`--listen [хост:]порт` — где принимать отладчик (по умолчанию только
`127.0.0.1`; `0.0.0.0:порт` — открыть для других машин), `--paused` — держать
программу до первой команды отладчика, `--once` — завершиться, когда отладчик
отключится. На нём же работают тесты TCP (`run_pvmdbg_tcp`).

### Программа на хосте (`--host`)

```
pvmdbg --host build/square.bin              # «устройство» — ВМ в этом процессе
pvmdbg --host build/square.bin --port COM3  # плата, на которую программа не прошита
```

Программа целиком остаётся на хосте, прошивать её не нужно. Хост работает как
фронтенд процессора: держит `PC`, выбирает инструкцию, декодирует и решает, что
с ней делать. Устройство — исполнительный блок: получает по одной инструкции
(`EXEC_INSTR`) и выполняет её на своём стеке, RAM, периферии и SVC, отвечая
статусом. Поэтому и ошибка исполнения видна сразу, с кодом и адресом.

На устройстве для этого есть только 8 байт в `PVMDbg_s` (`instr`,
`PVMDBG_CFG_INSTR_SIZE`), изначально заполненных `HALT`. На каждую
`EXEC_INSTR` область снова целиком заливается `HALT`, в её начало пишется одна
инструкция, `PC` ВМ переводится туда и выполняется один тик. После него `PC`
стоит на `HALT` за инструкцией, так что случайный `run` тут же остановится;
следующая инструкция опять начинается с начала области. Всё остальное —
стек, RAM, `code_ptr` программы — остаётся в структуре ВМ как есть, ничего не
сохраняется и не копируется. `STATE` в это время отдаёт `pc = 0xFFFF`: такого
адреса в программе нет.

| Инструкция | Кто выполняет |
|---|---|
| данные: `PUSH`, арифметика, `LOAD`/`STORE`, `ENTER`/`LEAVE`, `LOADFP`/`STOREFP`, `SVC`, … | устройство |
| `JMP` | хост: просто переносит `PC` |
| `JZ`/`JNZ` | хост читает вершину стека устройства, устройство делает `POP`, хост переходит или нет |
| `CALL` | пролог: устройству уходит `PUSH <адрес возврата>` (то же слово, что положил бы сам `CALL`, так что кадры, `ENTER`/`LEAVE` и смещения `LOADFP` совпадают с откомпилированными), `PC` переходит в функцию |
| `RET` | хост читает адрес возврата с вершины стека устройства, устройство делает `POP`, работа продолжается после `CALL` |
| `HALT` | конец |

Команды те же: `step`, `run`, `state`, `dis`, `break`/`clear`/`breaks` (точки
останова теперь хостовые и без лимита в четыре слота), `reset` (`PC` в 0,
стек устройства пуст); `stack` и `mem` по-прежнему обращаются к устройству.
Плюс `call` — выполнить одну функцию и встать:

```
(pvmdbg) call square 0 9
  pc=0x0011  sp=0  fp=0  function returned  [host: main]
  ...
  it left on the stack (arguments included), top first: 9 81
```

Слова после имени кладутся на стек в указанном порядке, как это сделал бы
вызывающий код (слот под результат — тоже аргумент, если так устроено
соглашение о вызовах), за ними — особый адрес возврата `0xFFFF`. `RET` на него
означает, что функция вернулась: всё, что лежит выше исходной глубины стека,
печатается и снимается, `PC` возвращается туда, где был. Имена функций берутся
из листинга `pvmc -l` рядом с `.bin`; без него — адресом (`call 0x12 0 9`).

`exec` — несколько инструкций посреди программы, которая остаётся, где стояла:

```
(pvmdbg) exec PUSH 1234; STORE 0
  snippet left nothing on the stack
(pvmdbg) exec LOAD 0; PUSH 1; ADD
  snippet left on the stack, top first: 1235
```

Код — строка инструкций через `;`, файл `.pvms` или `.bin` от `pvmc -f bin`;
ассемблирует тот же ассемблер, что и `pvmc`, строка проверяется против RAM и
стека, о которых сообщает устройство (`mem`). Выполняется сниппет так же, как
программа: данные — на устройстве по одной инструкции, переходы — на хосте,
адреса считаются от начала сниппета, `HALT` в конце не нужен. Видит он стек,
RAM, usrsect и SVC программы — можно прочитать или поменять переменную,
дёрнуть периферию. То, что он оставил на стеке выше исходной глубины,
печатается и снимается; `PC` программы, её точки останова и идущий `call` не
трогаются. Без `--host` `exec` не работает: устройство не хранит кода, а без
программы на хосте сниппету некуда вернуть `PC`.

Цена: каждая инструкция — один-два обмена кадрами. Локально это незаметно,
по порту на 9600 — около 35 инструкций в секунду (на 115200 было ~300); для
отладки хватает, для реальной работы — нет. Машинный режим (`--machine`) и VS Code этот режим
пока не умеют.

## В VS Code

Точки останова кликом по полю редактора, F5/F10/F11, подсветка текущей строки,
стек в панели переменных. Установка и `launch.json` описаны в
`Release/vscode-extension/README.md` (без ссылки: этот файл лежит и в
репозитории, и в `Release/docs/`, и относительный путь туда у них разный).

Расширение **не** разговаривает с платой само: оно запускает `pvmdbg --machine`
и обменивается с ним строками. Всё, что сложно или опасно — формат кадра, CRC,
COM-порт, пересборка кадра из потока, учёт точек останова на устройстве, —
остаётся в C, где оно уже проверено на железе. Вторая реализация протокола на
JavaScript — ровно то, что разъехалось бы с первой.

Машинный режим — построчный, по одной команде и одному ответу на строку:

```
> state          < ok pc=39 sp=11 fp=9 mode=0 reason=3
> break 39       < ok
> run            < ok
> poll           < ok running=1
> poll           < ok running=0
> stack 4        < ok n=2 v0=3 v1=5
> mem            < ok stack=1024 ram=64
```

Намеренно не JSON: через эту границу ходят только числа, поэтому пары
`ключ=значение` не требуют парсера ни с одной стороны. Имена файлов через неё
не ходят вовсе — карту отладки держит расширение, ему она нужна и так, чтобы
знать, какой файл подсветить.

`run` только запускает программу, а `poll` даёт ей продвинуться и говорит,
остановилась ли она. Разделены они затем, чтобы пауза оставалась возможной:
одна блокирующая команда «выполняться до остановки» сделала бы бесконечный цикл
неостанавливаемым, а фоновый поток в инструменте такого размера — лишняя
деталь, которая ломается.

Шаг в редакторе — по строкам исходника, а не по инструкциям: одна инструкция
обычно оставляет подсветку на том же месте, и F10 выглядел бы сломанным. F10 не
проваливается внутрь вызова (пока указатель кадра глубже начального — шагаем
дальше), F11 останавливается на первой же смене строки.

Чего в расширении пока нет: многокадрового стека вызовов (показывается один
кадр) и имён локальных переменных — стек виден значениями. И точек останова
больше четырёх: столько слотов у агента на устройстве.

## Сторона устройства

Главный цикл прошивки выглядит так (набросок есть и в `pvm/pvmdbg.h`):

```c
static PVM_Word_t vm_stack[PVM_CFG_STACK_SIZE];
static PVM_Word_t vm_ram[PVM_CFG_RAM_SIZE];

PVM_Init(&vm, code, len, vm_stack, PVM_CFG_STACK_SIZE, vm_ram, PVM_CFG_RAM_SIZE);
PVMDBG_Init(&dbg, &vm);

while(1){
  /* принять кадр в buf, len = сколько байт принято */
  PVMDBG_Poll(&dbg, buf, &len);
  if(PVMDBG_IsAccessExecTick(&dbg))
    PVM_ExecTick(&vm);
  /* если len > 0 — отправить buf наружу */
}
```

Стек и RAM — не часть `PVM_State_s`: это пулы, которые выделяет прошивка
(обычно статическими массивами нужного размера) и передаёт в `PVM_Init`; в
состоянии ВМ хранятся только указатели на них и их длины в словах. Так одна
прошивка может дать маленькой программе маленький стек без пересборки ВМ, а
отладчик — прочитать фактические размеры командой `MEM_INFO` (`mem` в утилите).
`PVM_Init` обнуляет оба пула и возвращает `ERRORCODE_BAD_CONFIG`, если стека
нет, он длиннее `0x7FFF` слов или RAM залезает в usrsect (`0x4000`).

`PVMDBG_Poll` разбирает кадр, исполняет команду и кладёт ответ в тот же буфер
(`len` на входе — сколько принято, на выходе — сколько отправить, `0` означает
«отвечать нечего»). Собственно исполнение программы командами не делается:
они лишь меняют то, что `PVMDBG_IsAccessExecTick` ответит на следующих витках
цикла.

Три момента в этой логике неочевидны, но важны:

- **`RUN` с точки останова.** Если `PC` стоит ровно на взведённой точке, её
  нужно пропустить один раз — иначе цикл будет бесконечно сообщать об одной и
  той же остановке, а программа не сдвинется ни на инструкцию.
- **`STEP` игнорирует точки останова.** Запросили одну инструкцию — она
  выполняется, даже если стоим на точке.
- **`HALT` — причина остановиться.** Выполнять его повторно бессмысленно, а
  цикл при этом крутился бы вхолостую. `PC` остаётся на `HALT`, то есть там,
  где отладчику его и надо показать.

По умолчанию `PVMDBG_Init` оставляет ВМ в состоянии «выполняется»: плата,
включённая без подключённого отладчика, должна работать. Утилита сразу после
подключения шлёт `PAUSE`, а уходя — `DETACH`. Прошивка, которая сама видит, что
отладчик ушёл (закрытое соединение, как в `pvmboard`), вызывает
`PVMDBG_Detach` — это то же самое.

## Протокол

Кадр фиксированный — 12 байт в обе стороны, little-endian:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | `sync` = `PVMDBG_SYNC` |
| 4 | 2 | `cmd` (`PVMDbgCmd_e`) |
| 6 | 4 | `data`, зависит от команды; неиспользованные байты — нули |
| 10 | 2 | `crc16` (CCITT) по 10 предыдущим байтам |

Длины в кадре нет: читателю не приходится доверять полю длины из потока,
который может быть испорчен, и обеим сторонам хватает одного 12-байтного буфера.
`PVMDBG_FrameLength` по накопленному куску отвечает: `12` — кадр целиком, `0` —
ждать ещё, `-1` — впереди не `sync`, надо выкинуть байт и спросить снова. Так
поток пересинхронизируется после помех. Цена — то, что в 4 байта не влезает,
запрашивается по частям: одно слово стека, один слот точек останова, 4 байта
кода за раз (на хосте это собирает `debugger/dbgclient.c`).

Кадр читается и пишется побайтово, а не кастом буфера к `PVMDbgFrame_s*`: у
буфера нет гарантии выравнивания, а чтение `uint32` с нечётного адреса на
Cortex-M0 — HardFault (та же причина, что у `_FetchWord` в `pvm.c`). Сборка и
разбор кадра (`PVMDBG_FrameBuild`/`PVMDBG_FrameParse`) вынесены в заголовок и
используются обеими сторонами — так две реализации одного формата не разъедутся.

16-битные значения — little-endian:

| Команда | `data` запроса | `data` ответа |
|---|---|---|
| `PING` `0x01` | — | — |
| `STATE` `0x02` | — | `pc`(2), `mode`(1), `reason`(1); `pc = 0xFFFF` — `PC` в области `EXEC_INSTR` |
| `READ_STACK` `0x03` | индекс от вершины (1) | слово(2), глубина стека(2); за дном — `ERROR` |
| `READ_CODE` `0x04` | адрес(2) | 4 байта байткода, за концом программы — `HALT`; адрес за концом — `ERROR` |
| `MEM_INFO` `0x05` | что(1) | `0`: размер стека, RAM (в словах); `1`: длина кода (байты), usrsect (слова) |
| `REGS` `0x06` | — | `sp`(2), `fp`(2) — глубины стека |
| `READ_DATA` `0x07` | адрес(2) | слово(2): RAM с `0`, usrsect с `0x4000`, как у `LOAD`; иное — `ERROR` |
| `RUN` `0x10` | — | — |
| `PAUSE` `0x11` | — | — |
| `STEP` `0x12` | — | — |
| `RESET` `0x13` | — | — |
| `DETACH` `0x14` | — | — (точки останова сняты, программа запущена; если `PC` был в области `EXEC_INSTR` — `PC`/`SP`/`FP` как после `PVM_Init`) |
| `BRKP_SET` `0x20` | адрес(2) | — |
| `BRKP_CLR` `0x21` | адрес(2) | — |
| `BRKP_LIST` `0x22` | слот(1) | адрес(2), взведён(1), слотов всего(1) |
| `EXEC_INSTR` `0x34` | опкод(1), операнд(2), длина 1 или 3(1); переходы, `CALL`/`RET`/`HALT` отвергаются; только когда ВМ остановлена | статус `PVM_ExecTick`(1, со знаком), `sp`(2) |
| `ERROR` `0x7F` | — | шлёт только устройство, вместо команды, которую не смогло выполнить |

`READ_DATA` адресует память так же, как `LOAD` и как листинг `pvmc -l` даёт
адреса переменных (`# variables:`), — поэтому значение переменной по её
адресу из листинга читается напрямую (`data` в утилите).

Кадр с неверной CRC остаётся без ответа: полю `cmd` в испорченном кадре верить
тоже нельзя, отвечать нечего. Значения кодов проставлены явно и с зазорами
между группами — они ходят между раздельно собираемыми хостом и прошивкой.

**Скорость на 9600 бод** (Nucleo-F429ZI, ST-LINK VCP): один обмен кадрами —
около 26 мс (2 × 12.5 мс на провод). Отсюда по командам утилиты: `state` —
~80 мс (три обмена: `STATE`, `REGS`, `READ_CODE`), `step` — ~130 мс, `mem` —
~80 мс, `data` — ~26 мс на слово, `stack`/`dis` — ~200 мс, остановка на точке
после `run` замечается в пределах 0.1–0.25 с (столько между опросами `STATE`).
`--host` — около 35 инструкций в секунду.

## Чего пока нет

- **Событий от устройства.** Об остановке хост узнаёт, опрашивая `STATE`, —
  само устройство ничего не инициирует. Событие превратило бы опрос в `run`
  в обычное ожидание.
- **Ошибок исполнения по протоколу.** `ERRORCODE_*` от `PVM_ExecTick` видит
  только цикл; в `STATE` они не попадают, поэтому в сессии против реальной
  платы такая ошибка не будет видна. Исключение — режим `--host`: там каждая
  инструкция приходит со своим статусом.
- **Многокадрового стека вызовов.** И утилита, и расширение показывают один
  кадр — тот, где стоим. Пройти по настоящему стеку — значит вычитывать с
  устройства сохранённые указатели кадров и понимать, какой функции
  принадлежит каждый адрес возврата.
- **Имён локальных переменных.** Стек ВМ показан значениями; чтобы вернуть
  смещениям кадра имена из `.hlc`, нужна ещё одна таблица рядом с картой
  строк.
