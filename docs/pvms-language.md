# Язык ассемблера PVM (`.pvms`)

Текстовый формат, который собирает `pvmc` в байткод PVM. Один файл — один
поток инструкций; управление потоком, функции и данные — через метки, `CALL`/
`RET` и фиксированные адреса RAM/периферии.

Конфигурация ВМ по умолчанию (см. `pvm/pvm.h`): стек данных — 1024 слова
(`PVM_CFG_STACK_SIZE`), RAM — 64 слова (`PVM_CFG_RAM_SIZE`, адреса `0..63`),
периферия/usrsect — начиная с `0x4000` (`PVM_CFG_USRSECT_BGN`). Слово —
16-битное знаковое (`PVM_Word_t` = `int16_t`). Если целевое устройство
сконфигурировано иначе — размеры объявляются прямо в исходнике директивами
`.code`/`.ram`/`.stack`/`.usrsect` (см. ниже). Сами пулы стека и RAM выделяет
прошивка и передаёт в `PVM_Init`, так что фактические размеры на плате задаёт
она; посмотреть их можно командой отладчика `mem` (см. `docs/debugger.md`). В
симуляторе их задают при запуске: `pvmsim program.bin --stack 256 --ram 128`.

## Синтаксис файла

```
# однострочный комментарий — до конца строки

.entry main          # с какой метки реально стартует программа
.import modulefile    # текстово подставить другой .pvms-файл
.const NAME 0x4000    # именованная константа
.var counter 0 1      # переменная: имя, адрес, размер в словах
.line 21 blink.hlc    # следующая инструкция — из этой строки .hlc

.code    8192         # сколько байт отведено под байткод
.ram     64           # сколько слов RAM у целевой ВМ
.stack   1024         # сколько слов в стеке данных
.usrsect 0x4000 8     # база и длина секции периферии

label:                 # метка — начинает новый блок кода
  MNEMONIC              # инструкция без операнда
  MNEMONIC 123           # инструкция с операндом (число, hex, .const-имя или метка)
```

- **Метка** — идентификатор (буквы/цифры/`_`) один в строке, оканчивающийся `:`.
  Начинает новый блок кода; на неё можно ссылаться как на адрес в операнде
  `JMP`/`JZ`/`JNZ`/`CALL`/`LOAD`/`STORE`/`LOADI`-адресах и т.д.
- **`.const NAME значение`** — именованная целочисленная константа (десятичное
  число или `0x...`). Подставляется всюду, где `NAME` используется как операнд.
- **`.var ИМЯ АДРЕС РАЗМЕР`** — то же самое, что `.const ИМЯ АДРЕС`, когда речь
  об операндах, но дополнительно сообщает, что это **переменная** известного
  размера: она попадает в карту памяти листинга, и проверяется, что весь её
  диапазон (а не только первое слово) помещается в секцию данных. Именно это
  `pvmcc` эмиттит для каждой глобальной переменной.
- **`.line НОМЕР путь`** — привязывает **следующую** инструкцию к строке
  исходника на `.hlc`. Байткода не занимает; путь — это весь остаток строки,
  без кавычек (как у `.import`): в путях Windows полно обратных слэшей и
  бывают пробелы, а правила кавычек — лишний повод ошибиться в файле, который
  человек руками не пишет. Привязка живёт на инструкции, а не на адресе,
  поэтому переезжает вместе с ней при перестановке блоков `.entry`. Эмиттит
  их `pvmcc`; собрать карту из них — `pvmc -g` (см. ниже).
- **`.func ИМЯ` … `.endfunc`**, **`.param ИМЯ СМЕЩЕНИЕ`**, **`.local ИМЯ
  СМЕЩЕНИЕ`** — символы для отладчика. Инструкции между `.func` и `.endfunc`
  принадлежат функции `ИМЯ`; `.param`/`.local` говорят, что переменная лежит
  в кадре по смещению `СМЕЩЕНИЕ` слов от `FP` и существует начиная со
  **следующей** инструкции (после `ENTER` для параметров, после
  инициализатора для локальных). Байткода не занимают, как и `.line`, и так же
  переезжают с инструкциями при `.entry`. Эмиттит их `pvmcc`; в `.pvms`,
  написанном руками, их может не быть вовсе.
- **`.import файл`** — текстово подставляет содержимое другого `.pvms`-файла на
  этом месте (как `#include`), путь ищется рядом с импортирующим файлом:
  сначала точное имя, потом с добавлением `.pvms`. Работает рекурсивно, с
  защитой от циклических импортов.
- **`.entry label`** — переносит на адрес `0` **весь непрерывный кусок кода**
  от `label` и до конца файла (включая метки внутри этого куска — они просто
  локальные цели переходов, а не отдельные функции), всё, что было в файле
  раньше — переносится следом. Без `.entry` код исполняется в том порядке, в
  котором написан, с адреса `0`.
- Операнд инструкции резолвится в таком порядке: имя `.const` → имя метки →
  число (десятичное или `0x...`, можно со знаком `-`).

### Размеры секций и контроль границ

`.code`, `.ram`, `.stack` и `.usrsect` описывают память **целевой** ВМ. Смысл
у них ровно один: то, что иначе стало бы ошибкой в рантайме
(`ERRORCODE_BAD_DADR`/`ERRORCODE_BAD_IADR` где-то посреди работы устройства),
становится ошибкой сборки.

| Директива | Единицы | Что проверяется |
|---|---|---|
| `.code N` | байты | итоговый размер программы; цели `JMP`/`JZ`/`JNZ`/`CALL` |
| `.ram N` | слова | адреса `LOAD`/`STORE` (валидны `0..N-1`) |
| `.usrsect БАЗА ДЛИНА` | слова | адреса `LOAD`/`STORE` в секции периферии |
| `.stack N` | слова | смещения `LOADFP`/`STOREFP` |

- Всё необъявленное берётся из `pvm/pvm.h`, поэтому файл без этих директив
  собирается ровно так же, как собирался раньше. Исключение — длина `usrsect`:
  константы для неё в `pvm.h` нет (ВМ узнаёт её в рантайме, из `PVM_UsrSect`),
  поэтому без явного `.usrsect` любой адрес от базы и выше считается
  допустимым. Проверка этой секции включается только объявлением.
- Проверяются только непосредственные операнды. `LOADI`/`STOREI` берут адрес со
  стека уже во время работы — статически про него ничего не известно, это
  по-прежнему забота рантайма. Про `.stack` аналогично: положение кадра
  известно только в рантайме, поэтому ловится лишь смещение, которое не может
  попасть в стек ни из какого кадра.
- Повторное объявление тем же значением (например, из `.import`) допустимо,
  противоречащее — ошибка.
- Отдельно проверяется, что операнд вообще влезает в 16-битное поле: раньше
  `PUSH 100000` молча терял старшие биты.

Готовый пример со всеми четырьмя директивами — `example/sections_demo.hlc`
(`.hlc`-уровень, см. `docs/hlc-language.md`); примеры того, что перестало
собираться, — в `example/bounds/`.

### Карта отладки (`-g`)

`pvmc … -g файл.dbgmap` собирает все директивы `.line` в плоскую таблицу
«адрес → файл и строка», по одной записи на строку, по возрастанию адреса:

```
0x0000 F:/Project/pvm/example/blink.hlc:19
0x0009 F:/Project/pvm/example/blink.hlc:21
0x0027 F:/Project/pvm/lib/time.hlc:14
```

Адреса здесь — уже итоговые, после перестановки блоков `.entry`. Имя файла
хранится рядом с номером не для красоты: `import` подставляет операторы одного
файла в другой, и «строка 14» без файла назвала бы место в том файле, про
который читатель случайно подумает. Эту карту читает `pvmdbg`, чтобы
показывать исходник и ставить точки останова по строке — см.
`docs/debugger.md`.

После строк идут символы — записи, начинающиеся с `@` (так их пропускает
всякий, кто читает только строки «адрес → строка»):

```
@func 0x0012 0x0021 square        # [начало, конец) — код функции
@var square param x -3 0x0013     # функция, вид, имя, смещение от FP, с какого адреса существует
@var total local sum 1 0x0125
@global RESULT 0x0000 1           # .var: адрес и размер в словах
```

По ним `pvmdbg` строит стек вызовов и показывает переменные по именам
(`bt`, `locals`, `print`, `globals`).

### Карта памяти в листинге

Листинг (`pvmc … -l файл.lst`) начинается с карты памяти — сколько занято в
каждой секции, с какого адреса начинается каждая функция и где лежит каждая
переменная:

```
# ---- memory map ----
#
# code    : 84 of 512 bytes
# ram     : 1 of 16 words
# stack   : 256 words
# usrsect : 0x4000..0x4007 (8 words)
#
# functions:
#   0x0000  main
#
# variables:
#   0x0000  total                  1 word   ram
#   0x4000  PERIPH_FIRST           1 word   usrsect
```

- Под **функциями** перечисляются только метки, на которые есть `CALL`, плюс
  точка входа: метки, сгенерированные компилятором (`if_end_7` и подобные),
  завалили бы список, а в самом листинге они и так видны.
- **Переменные** — это `.var`; обычный `.const` попадает в отдельный раздел
  `constants`, потому что число не обязано быть адресом.
- `ram: N of M` — не сумма размеров, а верхняя граница занятого: переменные с
  жёстким адресом могут оставлять дырки.

## Набор инструкций

Все инструкции — 1 байт опкода; те, что берут операнд, добавляют 2 байта
операнда (little-endian). `a`/`b` ниже — то, что было запушено раньше/позже
(`PUSH a; PUSH b; OP` ⇒ операция вида `a OP b`, если не указано иное).

### Стек

| Мнемоника | Операнд | Эффект |
|---|---|---|
| `PUSH n` | число | положить `n` на стек |
| `POP` | — | снять вершину |
| `DUP` | — | продублировать вершину |
| `SWAP` | — | поменять местами два верхних элемента |

### Арифметика и биты

| Мнемоника | Эффект |
|---|---|
| `ADD` `SUB` `MUL` `DIV` | `a + b`, `a - b`, `a * b`, `a / b` |
| `AND` `OR` `XOR` | `a & b`, `a \| b`, `a ^ b` |
| `SHL` `SHR` | `a << b`, `a >> b` (`a` — значение, `b` — величина сдвига) |
| `NOT` | `~вершина`, без снятия со стека (только инвертирует на месте) |
| `EQ` | `a == b` → `1`/`0` |
| `LT` | `a < b` → `1`/`0` |

Своих `>`/`<=`/`>=`/`!=` в ВМ нет — собираются из `LT`/`EQ` (см. таблицу в
`hlc/codegen.cpp`, ровно так это делает высокоуровневый компилятор):

```
a > b   ⇒  PUSH b; PUSH a; LT
a <= b  ⇒  PUSH b; PUSH a; LT; PUSH 0; EQ
a >= b  ⇒  PUSH a; PUSH b; LT; PUSH 0; EQ
a != b  ⇒  PUSH a; PUSH b; EQ; PUSH 0; EQ
```

### Переходы

| Мнемоника | Операнд | Эффект |
|---|---|---|
| `JMP addr` | адрес | безусловный переход |
| `JZ addr` | адрес | снять вершину, перейти, если она `0` |
| `JNZ addr` | адрес | снять вершину, перейти, если она не `0` |

### Память

| Мнемоника | Операнд | Эффект |
|---|---|---|
| `LOAD addr` | адрес (immediate) | положить на стек значение из RAM/периферии по `addr` |
| `STORE addr` | адрес (immediate) | снять вершину, записать по `addr` |
| `LOADI` | — | снять адрес с вершины, положить значение по нему (косвенное чтение) |
| `STOREI` | — | снять адрес (вершина), снять значение (следующее), записать |

Адрес меньше размера RAM — ячейка RAM; адрес от `0x4000` и выше (и в пределах
зарегистрированной периферийной секции) — обращение к периферии через
`PVM_UsrSect`. Любой другой адрес — ошибка выполнения `ERRORCODE_BAD_DADR`.
Обе границы настраиваются — см. «Размеры секций» выше.

Порядок для `STOREI`: `PUSH value; PUSH addr; STOREI` (адрес — последним,
он должен быть на вершине).

### Функции

| Мнемоника | Операнд | Эффект |
|---|---|---|
| `CALL addr` | адрес | положить адрес возврата, перейти на `addr` |
| `RET` | — | снять вершину как адрес, перейти туда |
| `ENTER` | — | пролог: сохранить текущий `FP`, `FP := SP` (открыть кадр) |
| `LEAVE` | — | эпилог: `SP := FP`, восстановить `FP` (оставляет адрес возврата на вершине для `RET`) |
| `LOADFP смещение` | знаковое число | положить на стек `FP[смещение]` |
| `STOREFP смещение` | знаковое число | снять вершину, записать в `FP[смещение]` |

`CALL`/`RET` сами по себе (без `ENTER`/`LEAVE`) — это всё, что нужно для
функции без аргументов и без кадра. `ENTER`/`LEAVE`/`LOADFP`/`STOREFP` нужны,
когда функция принимает аргументы через стек, возвращает значение через стек
или использует локальные переменные. Конвенция (её вручную видно в
`example/test_frame_pointer.pvms`, а автоматически её генерирует `pvmcc` —
см. `docs/hlc-language.md`):

```
main:                       func:
  PUSH 0    ; слот результата  ENTER
  PUSH 7    ; аргумент x       LOADFP -3    ; x
  CALL func                    LOADFP -3    ; x ещё раз
  POP       ; убрать копию x   MUL
  STORE R                      STOREFP -4   ; результат -> зарезервированный слот
  HALT                         LEAVE
                                RET
```

После `ENTER`: `FP[-1]` = сохранённый `FP`, `FP[-2]` = адрес возврата,
`FP[-3]` = последний запушенный аргумент, ..., `FP[-(2+N)]` = первый аргумент,
`FP[-(3+N)]` = зарезервированный вызывающим слот под результат (если он
нужен). Локальные переменные — положительные смещения `FP[0]`, `FP[1]`, ...
по порядку объявления. Каждый `LOADFP`/`STOREFP` проверяет, что адрес
попадает в границы стека, иначе — `ERRORCODE_BAD_DADR`.

### Вызовы в Си (SVC)

| Мнемоника | Операнд | Эффект |
|---|---|---|
| `SVC` | — | снять номер вызова с вершины, вызвать `svc_table[номер]` |

Номер вызова передаётся **через стек**, а не как immediate-операнд: `PUSH
номер; SVC`. Обработчик — обычная Си-функция `int (*)(PVM_State_s* state)`,
зарегистрированная заранее через `PVM_RegisterSvc(state, table, count)` (по
аналогии с `PVM_UsrSect` для периферии). Внутри обработчик сам снимает свои
аргументы и сам кладёт результат через `PVM_Pop`/`PVM_Push` — никакой особой
конвенции вроде `ENTER`/`LEAVE` для этого не нужно, это обычный синхронный
вызов Си-кода, а не PVM-функция. Неизвестный/незарегистрированный номер —
ошибка выполнения `ERRORCODE_BAD_SVC`.

```
PUSH 3    ; первый аргумент
PUSH 4    ; второй аргумент
PUSH 2    ; номер вызова: SVC #2 (Svc_Add в simulator/pvmenv.c)
SVC       ; обработчик снимет 4 и 3 через PVM_Pop и положит 7 через PVM_Push
```

В `simulator/pvmenv.c` сейчас зарегистрированы: `SVC #0` — `Svc_Tick`
(тик системного времени, см. `lib/time.hlc`) и `SVC #2` — `Svc_Add` (сумма
двух чисел); `SVC #1` свободен. Это одна конкретная
таблица, общая у симулятора и отладчика, а не часть языка — на реальном МК
номера и обработчики будут свои.

См. `example/test_svc.pvms` и обработчик `Svc_Add` в `simulator/pvmenv.c`.
